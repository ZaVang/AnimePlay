# AnimePlay 前端审计报告（2026-06-12）

> 审计方式：4 个维度的并行深度代码审计（页面功能 / 架构耦合 / 文档漂移 / 性能安全）+ 实际运行项目的视觉与交互审查（30+ 张界面截图，含登录态、战斗实况、移动端）。
> 审计范围：`frontend-vue/`（约 22,085 行 .ts/.vue）为主，`backend/server.py`、`api/index.py`、`docs/` 为辅。
> 所有结论附 `file:line` 或实测证据。仓库源代码零修改。

## 总评

**Overall: 4.0 / 10** —— 玩法野心和功能广度远超 demo 水准（8 个游戏模块、大部分核心循环能跑通），但被三类债务拖住：

- **结构债**：god store + 循环依赖 + 第二套战斗引擎内嵌在视图里
- **视觉债**：浅色主题改造只做了一半，全站处于新旧主题叠加态
- **信任债**：78% 的技能效果是假实现、爬塔进度会静默丢失

好消息：**`npm run type-check` 0 错误、运行时全页面 0 JS 异常**。地基没烂，值得修。

| 维度 | 得分 | 一句话 |
|---|---|---|
| Architecture | 4.5 / 10 | 有真实的分层意图（core/skills/stores），但被 14 处反向依赖和 3 个循环依赖架空 |
| Code Quality | 5 / 10 | 类型纪律好（22k 行仅 43 处 any），但 1561 行巨文件、84 次复制粘贴样板、150+ console.log |
| Engineering | 3 / 10 | 无可运行测试（未安装 vitest）、无 CI、无根 README、依赖锁失真 |
| Perf & Risk | 3.5 / 10 | 首屏 7.2MB（92% 浪费）、图片缓存被主动关闭、存档接口无鉴权 |

### 1.2 三个最伤玩家的功能断点

1. **理论战打赢了什么都不会发生（CRIT）**
   `TurnManager.endGame`（`src/core/battle/TurnManager.ts:413`）只 `setPhase('game_over')` + console.log；`gameStore.setWinner`（`src/stores/battle.ts:70`）全仓库 0 调用。没有结算界面、没有胜负提示、没有任何奖励发放——打理论战对经济系统毫无产出。结算数值表 `RewardCalculator.ts` 是现成的，只差最后一公里。

2. **爬塔进度静默丢失（CRIT）**
   `presetSquads` 与 `towerProgress` 只存在于 userStore 的 return 块（`src/stores/userStore.ts:1122,1146`），但 `saveStateToServer` 的 payload（`userStore.ts:274-285`）和 `loadStateFromServer`（`userStore.ts:210-263`）均不包含这两项。视图层又用 sessionStorage 存了一份层数（`SquadBattleView.vue:61-106`），刷新后出现"视图在第 5 层、store 认为第 1 层"的分裂，此时 `completeFloor(5)` 因 `floor !== currentFloor` 直接 no-op（`userStore.ts:1154-1160`）——**过层进度静默丢失，"历史最高"永远显示 1**。实测：登录有 175 条养成记录的老存档，3 支小队全部 0/4，确认链路。

3. **登出按钮是装饰品**
   `App.vue:56-59` 的「登出」button 无 `@click`；`userStore.logout()`（含登出前保存逻辑，`userStore.ts:327-332`）全仓库无人调用。

### 1.3 其他功能缺口

- **每日限购不生效**：`GachaShop.vue:237` 显示"每日限购: N"，但 `purchaseShopItem`/`purchaseFromShop`（`userStore.ts:501-608`）无任何限购计数，可无限购买。
- **两套升级结算并存**：`purchaseShopItem` 内部自带一套与 `addExp` 不同的升级逻辑（`userStore.ts:569-599`），行为不一致。
- **训练冷却可刷**：`NurtureActions.vue:35` 的 `trainingCooldowns` 只存组件内存，切页归零。
- **猜角色不持久化**：`guess.ts:87,96` 的 highScore/gameRecords 无任何保存；与主经济零联动。
- **音频设置整页占位**：`SettingsModal.vue:153-158` "音频功能开发中"。
- **设置关闭按钮死链**：`SettingsView.vue:4-12` 的 handleClose 只有 console.log。
- **理论战 AI 不会用角色技能**：`AIController.ts:83` TODO。
- **调试元素暴露给玩家**：对手手牌上方常驻"AI手牌数量: N"红字（`HandDisplay.vue:70-72`）；收藏页"启用虚拟化(>100张)"开发者开关直接面向用户。
- **UI 文案自相矛盾**：挑战塔同页同时写"每日最多挑战10次"（`SquadBattleView.vue:745`）和"无次数限制"（:622），代码实际无限制。

## 三、代码结构与耦合

**结论：不是"大量耦合和混乱"，而是"架构画对了、执行漏风了"。** 目录分层（views → components → stores → core → skills → utils → data/config/types）真实存在，types/config 层干净；但核心边界全部被打穿。

### 3.1 分层依赖现实（grep import 统计）

| 依赖方向 | 次数 | 判定 |
|---|---|---|
| core → stores | 14 处（battle store ×10、settings ×2、userStore、gameDataStore） | **反向，CRIT** |
| skills → stores / core | 1 + 3 处 | 反向（与 core→skills 成环） |
| utils → stores | 2 处（aiSquadGenerator、gachaRotation） | 反向 |
| views → core 直连 | 5 处 | 越层 |
| components → stores | 55+ 处（userStore ×27 居首） | 集中度过高 |
| data/config/types → 上层 | 0 | 干净 ✔ |

**后果**：战斗引擎无法脱离 Pinia/Vue 运行——无法 headless 单测、无法将来搬服务端复算、无法同时跑两场战斗。

**三处循环依赖（实锤）**：
1. `TurnManager.ts:87` → AIController → BattleController → TurnManager（import 写在文件中部正是与循环搏斗的痕迹，但静态 import 会提升，无效）
2. userStore ⇄ gachaStore（`userStore.ts:3` ↔ `gachaStore.ts:3`）；且保底**数据**在 userStore、保底**逻辑**在 gachaStore 直接改写（`gachaStore.ts:52-96`），所有权劈裂
3. core/systems ⇄ skills/effects 包级环

**运行时反向耦合**：`InteractionSystem.ts:35-50` 单例持有 `private interactionManager: any`，由 `BattleView.vue:46-50` 注入 Vue 组件实例——core 在运行时持有 UI 组件引用且类型为 any。

### 3.2 userStore 是 god object（1178 行，14+ 职责）

会话登录、玩家等级经验、三种货币、抽卡执行+入库、双卡池保底状态、抽卡历史、收藏/分解/收藏夹、卡组 CRUD、观看队列+统计、商店购买 ×2 套、养成全量（~260 行）、角色等级曲线数学、预设小队、爬塔进度、存档序列化/迁移、日志系统。

**已造成实际事故**：presetSquads/towerProgress 漏出存档协议（见 1.2.2）——god object 末端追加状态、persistence 没人同步的典型产物。

**拆分建议**（按数据所有权 + 保存粒度）：
- `profileStore`：会话+等级+钱包，唯一允许扣/加货币（暴露 `spend(type, amount): boolean` 守卫）
- `collectionStore` / `deckStore` / `nurtureStore` / `pveStore`（小队+爬塔）
- 保底+抽卡历史并入 gachaStore（解掉循环依赖，drawCards 移过去）
- 独立 `persistence.ts`：聚合各 store 的 serialize/deserialize/migrate，显式 schema 防"漏存"复发

### 3.3 技能系统：注册表是数据驱动的壳，效果本体是假实现（CRIT，信任债）

`skills/effects/index.ts`（1561 行）一个巨型对象字面量装 134 个 handler，**105 个（78%）是播报式假实现或简化偷换**：

- **播报式假实现**：如 `战场原黑仪_毒舌反击`（:190-198）——UI 弹出"对方辛辣点评 -3 强度"的通知，实际什么都没做，TP 照扣。**技能说明书与实际行为系统性背离**。
- **简化偷换**：如 `史派克_赏金猎人`（:1466-1476）要求"己方造成声望损失时 40%"，实现为任意触发 40%——触发条件错误。
- **正面范本只有 3 处**：如 `牧濑红莉栖_时间理论`（:152-173）真正使用 InteractionSystem + `PersistentEffectSystem.addCardTypeStrengthBonus(playerId,'科幻',2,1)`——**正确的参数化原语已经存在，只是 95% 的 handler 没用它**。
- 样板重复：`ctx.playerId === 'playerA' ? ... : ...` 取名逻辑重复 **84 次**；一个 `getActor(ctx)` 可删几百行。

### 3.4 两套战斗 = 两套引擎零共享

- BattleView（245 行）走 core 引擎 + battle store + 10 个子组件，是全仓分层最好的视图（script 仅 108 行）——**证明项目不是不会分层**。
- SquadBattleView（985 行，59% 是 script）把第二套回合制引擎整个内嵌在 .vue 里，含 6 个本应属于其他层的子系统（sessionStorage 持久化、战力计算、回合引擎、经济结算、AI 调度、自动战斗 setTimeout 链）。
- **公式逐行复制**：`SquadBattleView.vue:335-351` 与 `utils/battleCalculator.ts:57-78` 伤害/暴击公式逐行相同——而该视图明明 import 了 battleCalculator 却重抄；`autoFinishBattle`（:489-564）与 `executeRound`（:286-332）整块复制只差 setTimeout 时长。
- 当前层数三处双写：userStore.completeFloor / 视图本地 ref / sessionStorage。

### 3.5 配置散落

`config/gameConfig.ts` 对老系统覆盖良好（概率/保底/分解集中且带平衡注释 ✔），但新系统全部绕过它：

- 养成整张经济表写在组件里（`NurtureActions.vue:74-218`、`InteractionPanel.vue:27-78`，调平衡靠改组件）
- **组件直改货币余额，绕过 store（CRIT）**：`NurtureActions.vue:239,288,412`、`SquadBattleView.vue:401` 直接 `userStore.playerState.knowledgePoints -=/+=`——经济无事务入口，无法防负数、无法审计
- 小队战奖励公式内联在视图（:375-440）；AI 数值与展示文案双写（`aiSquadGenerator.ts:199-208` vs :140-158，改数值不改文案即 UI 说谎）

### 3.6 做得好的（公允部分）

1. types 层克制干净：4 文件 114 行，`| (string & {})` 保留字面量提示的地道技巧；全 src 仅 43 处 any（22k 行体量下相当低）
2. 计算层纯函数意识：`BattleEngine.resolveClash` 明确文档化 pure function；BattleEngine/StrengthCalculator/RewardCalculator 可测试性最好
3. 效果注册表骨架正确：缺失 handler 警告 + try/catch 隔离单技能崩溃；`animeDefaultEffects.ts` 是真数据驱动正例
4. 生成数据工程化：`scripts/generateUrSkills.js` 入库、生成文件带"勿手动编辑"头
5. 路由全懒加载；主数据加载完成后再挂载
6. 存档迁移意识：旧格式 number → {count} 迁移、Map/Set 序列化正确
7. 配置带平衡 rationale 注释；抽卡概率全配置化无硬编码
8. 测试工具有 DEV 门控意识（`BattleView.vue:21-24`；瑕疵：`DeckEditor.vue:11` 未同样门控）

## 四、前端审美

**结论：信息架构和组件骨架在线，审美能力是有的；但"浅色暖调主题改造"只做了一半，全站处于新旧主题叠加态。缺的不是品味，是一次系统性还债。**

### 4.1 三处硬伤

1. **全站标题泛白（最高优先级视觉 bug）**
   首页"玩家状态/观看队列/系统日志/我的喜爱/观看统计"、挑战塔"当前进度/选择挑战小队/小队A·B·C"、养成"羁绊等级/养成属性"、战斗"请选择您的出战卡组"——全部白字压米黄底，几乎不可读。
   **根因**：46 个文件里 **172 处硬编码 `text-white`**（如 `PlayerStatus.vue:15`），深色主题时代遗产；主题系统只迁移了背景 CSS 变量，没迁移文字色。修完这一项，观感跳一个档次。

2. **配色没有系统**
   同一个商店页面四个"购买"按钮分别是靛蓝/紫/橙/青绿；导航青绿、抽卡 CTA 紫、限时池橙金、养成粉。主题定义了 6 套配色变量，但组件层大量颜色不走变量。战斗日志还是一块深灰盒子杵在奶油色页面上（旧深色主题残留）。

3. **移动端完全不可用**
   390px 宽度下侧边栏不收纳、占一半屏宽，数值一字一行竖排断行。没有任何响应式适配。

### 4.2 其他视觉问题

- 抽卡结果弹窗毫无仪式感（白盒+卡+确认按钮）——抽卡是这类游戏唯一的多巴胺时刻，目前是全站最寒酸的弹窗
- 战斗阵容有裂图，`<img>` 无 onerror 兜底（部分角色图缺失时直接显示裂图图标）
- 收藏页冷启动大量白卡（图片无缓存+无缩略图导致加载慢，见性能节，给足时间能加载出来）
- 主页满级显示 "32055 / Infinity EXP"（边界态文案未处理）
- `index.html` 标题 "Vite App"
- Tailwind 动态类失效：`bg-${color}-600/10`（`NurtureActions.vue:678` 等 3 处）JIT 无法静态提取，状态底色静默丢失

### 4.3 好看的部分

设置页主题选择卡（全站最现代）；卡组编辑器双栏布局（专业）；小队战对阵图（头像+序号+血条，干净易读）；猜角色像素化界面（简洁成立）；抽卡历史统计图表（chart.js 占比图有模有样）；小队选人弹窗（卡面+渐变名牌+稀有度徽章）。

## 六、全前端架构评估（要不要拆后端）

**直接回答：作为单机自娱项目，行，甚至是合理的省力选择；但有两条红线现在就该处理，且一旦想做排行榜/对战，权威逻辑必须搬家。**

现状本质：Flask 只是"带文件柜的静态服务器"。所有游戏规则——抽卡 RNG、保底、战斗判定、货币增减（全仓 88 处 `Math.random` / 18 文件）——都在客户端；存档以明文 JSON 全量覆盖写到 `data/user_data/`。

**现在就该修的两条红线**（与拆不拆后端无关）：
1. 存档接口加最小鉴权（哪怕共享密码/简单 token）
2. 关掉 `debug=True`

vite 配置注释写着"隧道场景需要"——只要隧道开过，这两个洞就真实暴露过。

**可以一直留在前端的**：战斗演出/动画/对话系统、主题与设置（已正确用 localStorage）、猜角色等无排行诉求的本地玩法、AI 决策、客户端预测渲染。

**将来做排行榜/PvP/好友时必须搬后端的**（届时不可信任何客户端上报）：
- 抽卡执行与保底状态（`gachaStore.performGachaLogic` 整段）
- 战斗结算与胜负判定（BattleController / SquadBattle 引擎 / battleCalculator）
- 货币与资源增减、收藏/卡组写入校验（防伪造 UR 满收藏）
- 用户身份（密码/token）

**务实的中间路线**：不必现在重写后端。但"core 层解除对 Pinia 的反向依赖"（见 3.1）就是在为这一天铺路——引擎一旦变成纯 TS 模块，前端跑是单机、放到 Node 服务端跑就是权威服务器，同一份代码。这是"今天还结构债 = 明天省重写"最实在的一例。
